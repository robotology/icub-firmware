# freertos

The FreeRTOS kernel **V11.2.0**, unmodified, built with Arm Compiler 6 (armclang) as a library for the Cortex-M4F of the
STM32H7 dual-core. It is the RTOS behind `embot::os::rtos` when the application defines `EMBOT_USE_rtos_freertos`
(`embot/os/embot_os_rtos_freertos.cpp`), as an alternative to the cmsisrtx lib (RTX5) and `EMBOT_USE_rtos_cmsisrtx`.

| lib | core | notes |
|---|---|---|
| `lib/freertos.debug.cm4.lib` | Cortex-M4F | `configASSERT()` on, stack overflow check (method 2) on, Event Viewer bridge on (`FREERTOS_EVENTVIEWER`): the application must link `libs/midware/eventviewer/src/eventviewer.c` |
| `lib/freertos.fast.cm4.lib` | Cortex-M4F | `FREERTOS_FAST`: no `configASSERT()`, no stack check, no Event Viewer (as `cmsisrtx.fast.*`) |
| `lib/freertos.debug.cm7.lib` | Cortex-M7 (DP FPU) | as `freertos.debug.cm4.lib` |
| `lib/freertos.fast.cm7.lib` | Cortex-M7 (DP FPU) | as `freertos.fast.cm4.lib` |

`proj/freertos.uvprojx` has four targets, named as those of cmsisrtx: `debug.cm4`, `fast.cm4`, `debug.cm7` and `fast.cm7`.
Each one builds `obj/<target>/freertos_<flavour>_<core>.lib` and its post-build step copies it to
`lib/freertos.<flavour>.<core>.lib` (uVision cuts a dotted `OutputName` at the last dot, so the dots are added by the
copy). The CM7 targets use the same port `GCC/ARM_CM4F`: it is valid for the Cortex-M7 r1p0 and later, as the CM7 of the
STM32H7 (the port `ARM_CM7/r0p1` is only for the errata of the r0p1). The four libs use the same `api/`: the application
changes only the lib it links. No CMSIS-Pack / RTE component is used: everything needed is in this folder.

The port is `GCC/ARM_CM4F`, the one that FreeRTOS indicates for armclang. It is also the right one for the Cortex-M7 of
the STM32H7 (revision r1p1 / r1p2, not r0p1): a `cm7` target can be added with the same sources and `CPUTYPE("Cortex-M7")`.

## What is in the lib
`tasks.c`, `queue.c`, `list.c`, `timers.c` (no event groups, no stream buffers, no co-routines), `port.c` of
`GCC/ARM_CM4F` (`SVC_Handler`, `PendSV_Handler`, `SysTick_Handler`: the names of the vector table are given to the
handlers of the port by `FreeRTOSConfig.h`), and `cfg/freertos_lib.c`. No `heap_x.c`: the kernel has no heap
(`configSUPPORT_DYNAMIC_ALLOCATION = 0`), every object is created with the static API and memory given by the
application (in `embot::os::rtos` with `new`), as cmsisrtx does with the `cb_mem` of RTX.

## How to use it in an application
1. link `lib/freertos.debug.cm4.lib` (or the fast one, or the cm7 ones on the CM7);
2. add the path `libs/highlevel/abslayer/freertos/api` and `#include "freertos_api.h"` (only `embot_os_rtos_freertos.cpp`
   does it in an embot application);
3. define `EMBOT_USE_rtos_freertos` (instead of `EMBOT_USE_rtos_cmsisrtx`) and keep `embot/os/embot_os_rtos.cpp` in the
   project: it includes `embot_os_rtos_freertos.cpp`;
4. the application must provide `SystemCoreClock`; `SysTick_Handler`, `SVC_Handler`, `PendSV_Handler` are the ones of the
   lib (they override the weak ones of the startup file). `tasks.c` references `xPortStartScheduler()` of `port.c`, so the
   object with the handlers is pulled from the lib; if a weak handler still wins, check the map file
   (`configCHECK_HANDLER_INSTALLATION = 1` makes `configASSERT()` stop at the start if the vector table is wrong).

Example: `board/amcmj1/examples/freertos-blink` (target `amcmj1.2cm4-master` of `proj/amcmj1.freertos.blink.uvprojx`).

## The API header

`api/freertos_api.h` (source `src/extra/freertos_api.h`) includes `FreeRTOS.h`, `task.h`, `queue.h`, `semphr.h`,
`timers.h` and declares what `cfg/freertos_lib.c` adds:

- `freertos_config_set(const freertos_config_t *)`: tick frequency and memory of the stacks of the idle and timer tasks,
  set at run time before `vTaskStartScheduler()`. `embot::os::rtos::scheduler_init()` calls it with the values of
  `scheduler_props_t::prepare()`, as it calls `cmsisrtx_config_set()` with cmsisrtx. It returns `FREERTOS_CONFIG_OK`,
  `_ERR_PARAM` (nothing changed) or `_ERR_STATE` (scheduler already running). Without it: 1000 Hz and small static stacks.
- `freertos_tick_interval()`, `freertos_tick_count()`, `freertos_tick_overflow()`: as `OS_Tick_GetInterval()` & co of
  CMSIS, for the time in microseconds of `embot::os::rtos::scheduler_timeget()`.
- `freertos_error_notify(code, object)`: called by the hooks of the kernel (stack overflow, assert). Weak in the lib,
  redefined by `embot_os_rtos_freertos.cpp`: it prints with `embot::core::print()`, calls the `onOSerror` of
  `embot::os` and stops. Also `freertos_assert_failed(file, line)` and `vApplicationIdleHook()` are weak.

The name is not `freertos.h` because on Windows it would be the same file as `FreeRTOS.h`.

Run `python3 src/extra/make_api.py` (from any folder) after any change of `cfg/FreeRTOSConfig.h`, of
`src/extra/freertos_api.h` or of the kernel: the application must see the same `FreeRTOSConfig.h` used by the lib, because
the sizes of `StaticTask_t`, `StaticQueue_t`, ... depend on it. Then rebuild the lib.

## What is fixed at build time (FreeRTOSConfig.h, rebuild the lib to change)
- `configMAX_PRIORITIES` (56): the values of `embot::os::Priority` (those of `osPriority_t`) are used as they are. The
  init thread has priority 54 (as `osPriorityRealtime6`), the timer task 55 (as `OS_TIMER_THREAD_PRIO` of RTX). With more
  than 32 levels the port optimised task selection is off.
- `configUSE_TIME_SLICING` (0): no round robin among tasks of the same priority, as `OS_ROBIN_ENABLE = 0`.
- `configTIMER_QUEUE_LENGTH` (32): as the timer queue of `embot_os_rtos_cmsisrtx.cpp`.
- `configCHECK_FOR_STACK_OVERFLOW` (2), `configASSERT()` on: as the debug lib of cmsisrtx. Both off in
  `freertos.fast.cm4.lib` (`FREERTOS_FAST`).
- `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` (1): see below.
- the tick is NOT fixed: `configTICK_RATE_HZ` is the variable `freertos_tick_rate_hz`, set by `freertos_config_set()`.

## The C library (armclang)
The Arm C library calls `_mutex_initialize()`, `_mutex_acquire()`, `_mutex_release()` around `malloc()`, `free()`, the
streams of stdio, ... `cfg/freertos_lib.c` defines them with the suspension of the scheduler (`vTaskSuspendAll()`), so the
heap used by `operator new` is thread safe, as RTX does in `rtx_lib.c`. Before the start of the scheduler they do nothing.
Do not allocate in an ISR (as with cmsisrtx). There is a single libspace (no per-thread `errno`). They are not compiled with
GCC: with ATfE (picolibc) the equivalent hooks are to be added.

## What is different from RTX (cmsisrtx), and why it matters in embot
1. **ISRs that call the RTOS must have NVIC priority >= 1.** FreeRTOS masks the interrupts with BASEPRI, which never masks
   priority 0. An ISR with priority 0 must not call `embot::os::rtos` (e.g. `setEvent()` from a callback of embot::hw).
   With `configASSERT()` on, `vPortValidateInterruptPriority()` stops in `freertos_assert_failed()` if it happens. On the
   amcmj1 today the SPI1/2/3 IRQs and TIM1_UP use priority 0: their callbacks must not set events of threads, or their
   priority must become >= 1 when an application uses FreeRTOS. RTX has no such constraint.
2. **Before the start of the scheduler, any API call of FreeRTOS that creates an object (task, queue, mutex, ...) leaves
   the interrupts masked (BASEPRI) until `vTaskStartScheduler()`.** It is a design choice of FreeRTOS. embot creates the RTOS
   objects after the start (in the init thread), except the init thread itself, which is created just before the start.
   Code that creates mutexes or queues during `embot::hw::bsp::init()` and then waits for an interrupt would block.
3. **Timers are commands to the timer task.** Start, stop and delete are queued and executed by the timer task (priority 55,
   so at once when called from a thread). `embot_os_rtos_freertos.cpp` does not wait inside the timer task nor in an ISR,
   and releases the memory of a deleted timer only after the timer task has processed the deletion
   (`xTimerPendFunctionCall()`, the queue is FIFO).
4. **The idle hook never returns.** The `onidle()` of `embot::os::theScheduler` is a forever loop called by
   `vApplicationIdleHook()`: the idle task does not clean the tasks that delete themselves (only the init thread does it, and
   its memory is not released anyway).
5. **The TCB does not keep the entry function of a task.** The Event Viewer needs it (see below): whoever creates a task
   tells it with `freertos_ev_name()`. `embot_os_rtos_freertos.cpp` does so for every thread of embot.
6. **`xTaskNotify()` on a deleted task resurrects it** if the task was waiting for a notification. So `thread_delete()`
   first deletes the periodic timer that `thread_period_set()` gave to the thread, which would otherwise keep notifying it
   (found by the test of the Event Viewer: a deleted periodic thread was running again).

## The Event Viewer of uVision
As with cmsisrtx (`cmsisrtx_eventviewer.c`), `freertos.debug.cm4.lib` shows the running thread in Debug / OS Support / Event Viewer
(ULINKpro, trace on, ITM port 31), each thread named after its entry function (e.g. `tCTRL`):
- `FreeRTOSConfig.h` maps the trace macros `traceTASK_CREATE()`, `traceTASK_SWITCHED_IN()` and `traceTASK_DELETE()` of
  `tasks.c` to `freertos_ev_created()`, `freertos_ev_switched()` and `freertos_ev_deleted()` of `cfg/freertos_eventviewer.c`;
- the ITM messages are sent by `libs/midware/eventviewer` (`eventviewer_load()`, `_unload()`, `_switch_to()`): add
  `eventviewer.c` to the application, else the link fails (strong references, as in cmsisrtx);
- names: the threads of embot get the name of their entry function via `freertos_ev_name()`, called by
  `embot_os_rtos_freertos.cpp` after `xTaskCreateStatic()` with the scheduler suspended (the new task cannot run unnamed);
  the idle task is id 1 named `sysIDLE`, the timer task `sysTIMER`, the init thread `sysINIT` (sticky: it stays after the
  thread is gone). The id 2 is not used, the threads use the ids 3 ... 95;
- all the names are announced again 10 ms after the start and then every second, so the viewer gets them also when its
  window is opened late (`FREERTOS_EV_REANNOUNCE_S`, `FREERTOS_EV_FIRST_REANNOUNCE_MS`);
- `freertos_ev_diag` (Watch window) counts what the bridge did; `unnamed` counts the switches to a task created without
  `freertos_ev_name()`, shown as idle;
- the switch is notified when `vTaskSwitchContext()` elects the next task inside PendSV: a few cycles before the real
  switch. The cost is one ITM write per context switch: for measures use `freertos.fast.cm4.lib`.

## Verification
`embot_os_rtos_freertos.cpp` and this lib were tested on QEMU (machine `mps2-an386`, Cortex-M4F, GCC 13.2): 40 checks on
threads, priorities, events (any, all, timeout, other bits, from an ISR at priority 5), message and callback queues, timers (periodic,
one shot, restart, stop, delete from their own callback, no memory leak over 200 create + delete), periodic threads,
recursive mutexes and `Lock`, semaphores released by a timer, scheduler lock, `scheduler_timeget()` and `scheduler_timeset()`,
a deleted periodic thread that must not run again. All passed, also with the lib built as `freertos.fast.cm4.lib`, and the same for the Cortex-M7 on the QEMU machine
`mps2-an500`. With the
lib built as `freertos.debug.cm4.lib` and a stub of `eventviewer_*` (QEMU has no ITM), 9 more checks on the Event Viewer bridge
(names, ids, unload, switches, periodic announce) passed. Two more runs check the error paths: an ISR at priority 0 that calls `event_set()` stops in
`freertos_assert_failed()` (`vPortValidateInterruptPriority()`), and a thread that overflows its stack is reported by
`freertos_error_notify(FREERTOS_ERROR_STACK_OVERFLOW)` from PendSV. The sources also compile with clang 18 in armclang mode.
The run on the amcmj1 with `freertos.debug.cm4.lib` (without the Event Viewer bridge) was done; the Event Viewer is to be seen on
the board with the ULINKpro.
